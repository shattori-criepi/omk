# ハードウェアと実行環境

## 1. 目的

本書は、Raspberry Pi、Windows、ESP32、およびOMK周辺機器の役割と、ホストOS・コンテナ・アプリケーションの責務分担を定義します。

OMKでは、同じコードがすべての環境で同じ周辺機器へ接続できる必要はありません。重要なのは、**同じアプリケーション契約を実機ドライバとモックドライバが満たすこと**です。

## 2. 対応環境の位置付け

| 環境 | 状態 | 主な用途 | 実機アクセス |
|---|---|---|---|
| Raspberry Pi 4 | 正式対応 | 新OMKの実機運用、周辺機器試験、長時間試験 | あり。64-bit Raspberry Pi OSのみ |
| Raspberry Pi 5 | 正式対応 | 新OMKの実機運用、周辺機器試験、長時間試験 | あり。64-bit Raspberry Pi OSのみ |
| Raspberry Pi 3以前 | 対象外 | 現行OMKの調査・比較に限る | 新OMKの正式対応なし |
| 未評価の将来Raspberry Pi | 対象外 | 対応追加前の評価対象 | 実機試験完了まで正式対応なし |
| Windows 11 + Docker Desktop/WSL2 | 採用 | 日常開発、UI、単体・統合テスト、任意のスマートメータ実機検証 | モックを基本とし、BルートUSBは必要時のみ接続 |
| Linux PC | 採用可能 | CI、開発、シミュレーション | 原則モック |
| ESP32 | 採用 | センサ側ノード | センサへ直接接続 |

新OMKはRaspberry Pi 4とRaspberry Pi 5の両方を正式対応機とします。正式対象OSは64-bit Raspberry Pi OSのみで、コンテナはARM64を対象とします。32-bit Raspberry Pi OSは正式対象外です。採用するOSリリース、最小メモリ、ストレージ構成は別途確定します。将来モデルを追加する場合は、CPUアーキテクチャ、OS、Bluetooth、USB、ディスプレイ、Dockerイメージの試験結果を残した上で正式対応へ追加します。

## 3. 役割分担

### 3.1 Raspberry Pi

Raspberry Pi 4とRaspberry Pi 5は中央ゲートウェイです。

- Wi-SUN/Bルート機器への接続
- Bluetooth機器への接続
- USB／シリアル機器への接続
- ESP32からのMQTT受信（第一候補のWi-Fi＋MQTT）
- ローカル保存
- ディスプレイ表示
- 本番ではLTE等の独立回線による外部送信
- 所内・開発環境では必要に応じてEthernetまたはWi-Fiによる外部送信
- OMK用Wi-Fiアクセスポイントの提供
- コンテナの起動・監視

### 3.2 Windows

Windowsはハードウェア非依存部分を開発する標準環境です。Bルート対応USBドングルを使う経路は、利用できる開発者が開発中にスマートメータ実機を確認するための任意検証環境です。

- センサシミュレータを起動する
- MQTTテストメッセージを生成する
- ドメインロジックとデータ変換を検証する
- UIを開発する
- 通信断、異常値、再送を疑似的に再現する
- Raspberry Pi向けイメージのビルド可否を確認する
- 必要な場合のみ、BルートUSBドングルによるスマートメータ実機の接続、認証、計測、切断、再接続を検証する

Windows固有コードを本番ロジックへ追加して実機との差を埋めないでください。USB転送、デバイスパス、権限の差はアダプタ、設定、Compose差分で吸収します。通常の開発とCIはモックで完結させ、Windows経路を本番保証の要件には含めません。正式な実機保証はRaspberry Pi 4とRaspberry Pi 5の両方で確認します。

### 3.3 ESP32

ESP32はセンサ近傍へ置くノードです。通信方式はOMK用Wi-Fi＋MQTTを第一候補とし、初期設計・試作もこの方式を優先します。BLEは代替または併用候補として比較します。

- GPIO、I2C、SPI、UART等でセンサ値を取得する
- 最小限の校正・範囲確認を行う
- Wi-Fi方式では共通契約に沿ったMQTT payloadを送る
- BLE方式でも同じ共通計測契約へ変換できるデータを提供する
- 起動、再接続、ファームウェア、電波状態等をstatusとして送る
- 複雑な長期保存やクラウド固有処理を持たない

### 3.4 ネットワーク

本番設置では、設置先住宅のWi-FiまたはLANを動作要件にしません。

- Raspberry Pi 4またはRaspberry Pi 5をOMK用Wi-Fiアクセスポイントとして動作させる
- ESP32等の無線センサノードはOMK用ネットワークへ接続する
- 外部送信はLTE等、住宅ネットワークから独立した回線を基本とする
- 所内試験、開発、保守ではEthernetまたは既存Wi-Fiを利用してよい
- AP、ルーティング、DNS、LTE接続はホストOS側の責務とする
- アプリケーションは外部ネットワークを通常のIP接続として利用する

Wi-Fi＋MQTTではなくBLEを採用するセンサノードがある場合でも、住宅Wi-Fiへ依存しない原則は維持します。

## 4. 想定周辺機器

### 4.1 スマートメータBルート

想定:

- Wi-SUN USBドングル
- シリアルデバイスまたはUSB CDCとして認識
- BルートID・パスワードを使用
- 瞬時電力、積算電力量等を取得

利用環境:

- Windows 11＋WSL2／Docker: 開発中に必要な場合だけ行う、スマートメータ実機との任意検証
- Raspberry Pi 4およびRaspberry Pi 5: 正式な実機確認、長時間試験、本番運用

設計要件:

- Windowsの任意検証経路とRaspberry Pi 4／5で同じBルートアダプタ契約を利用する
- USB転送方式やデバイスパスの差を設定とCompose差分へ隔離する
- ドングル型番をアプリケーション層へ漏らさない
- シリアルパスを設定で指定する
- 再接続可能にする
- 認証情報をログへ出さない
- 生フレームを必要に応じてデバッグ保存できるが、本番では既定で無効にする
- 同じ記録データを用いたリプレイテストを用意する

### 4.2 Bluetoothワットチェッカー

想定:

- Raspberry PiのBluetoothまたはUSB Bluetoothアダプタを利用
- D-Bus／BlueZ経由で接続
- 機器固有GATTやプロトコルをドライバ内へ隔離

設計要件:

- Bluetoothアドレスや識別情報を設定化する
- 接続・切断・再探索を状態機械として扱う
- スキャンし続けてCPUや無線帯域を消費しない
- 1台の切断で他センサ処理を止めない
- Windowsでは同じ計測契約を満たすモックを使う

### 4.3 LTE USBドングル

想定:

- SORACOM Onyx等
- USB接続
- Raspberry Pi OS側で回線接続を管理

設計要件:

- 接続確立、APN、モデム制御はホストOS側で行う
- アプリは通常のIPネットワークとして利用する
- アプリがモデムを直接再設定しない
- 外部疎通、DNS、送信先到達性を別々に診断できる
- 回線断時も計測・保存を継続する
- データ使用量を抑えるため、送信バッチと圧縮を設定可能にする

### 4.4 公式7インチディスプレイ

想定:

- Raspberry Pi公式7インチタッチディスプレイ
- ローカルWeb UIをキオスク表示

設計要件:

- 画面回転、解像度、輝度、スクリーンセーバ、ブラウザ自動起動はホストOS側で設定する
- UIはタッチ操作を前提にしつつ、操作しなくても主要状態が分かる
- 夜間の輝度低下または画面消灯を設定可能にする
- UI停止が計測停止につながらない
- UIは`core`の公開APIだけを利用する

### 4.5 その他のセンサ

例:

- 温度
- 湿度
- CO2濃度
- ドア開閉
- 騒音
- 照度

追加時は、目的、設置負担、電源、通信、校正、交換性、データ量を確認します。

## 6. デバイスのコンテナ公開

### 6.1 USB・シリアル

実デバイス名`/dev/ttyUSB0`は接続順で変化する可能性があります。udevルールで安定したシンボリックリンクを作ることを推奨します。

例:

```text
/dev/omk-wisun
/dev/omk-modem
```

Composeでは必要なデバイスだけを渡します。

```yaml
services:
  core:
    devices:
      - /dev/omk-wisun:/dev/omk-wisun
```

デバイスアクセスのためにコンテナ全体を特権化しません。

### 6.2 Bluetooth

BlueZをホストで動かし、必要に応じてD-Busソケットを対象コンテナへ読み書き可能でマウントします。

```yaml
services:
  core:
    volumes:
      - /run/dbus/system_bus_socket:/run/dbus/system_bus_socket
```

実際に必要な権限は使用ライブラリとOS構成で確認します。ホストネットワークや追加capabilityを与える場合は、理由を文書化してください。

### 6.3 ディスプレイ

原則としてUIコンテナはHTTPで画面を配信し、ホスト側ブラウザが表示します。X11／Waylandソケットをアプリコンテナへ直接渡す構成は、必要性が確認できるまで採用しません。

## 7. udevルール

### 7.1 目的

- 再起動や接続順によるデバイス名変化を防ぐ
- デバイスごとに最小限の権限を与える
- 複数機器を安定して識別する

### 7.2 方針

- USB vendor/product IDだけでなく、可能ならserial numberも使う
- 汎用的すぎるMODE設定を避ける
- アプリ実行ユーザー／グループへ必要な権限だけを与える
- ルールと確認手順を`config/udev/`または`scripts/host-setup/`へ置く

例の形式:

```udev
SUBSYSTEM=="tty", ATTRS{idVendor}=="xxxx", ATTRS{idProduct}=="yyyy", SYMLINK+="omk-wisun", GROUP="dialout", MODE="0660"
```

実値は対象機器を確認してから設定します。

## 8. Raspberry Pi 4／5のホストセットアップ

最低限確認する項目:

1. Raspberry Pi 4とRaspberry Pi 5それぞれについて、採用する64-bit Raspberry Pi OSとARM64イメージの組み合わせ
2. Docker EngineとCompose plugin
3. OS時刻同期
4. USB／シリアルデバイス認識
5. Bluetoothの起動と対象機器の検出
6. LTE回線の接続と自動再接続
7. ディスプレイ向き・輝度・キオスク
8. udevルール
9. ログ・データ保存領域
10. 自動起動と安全な停止

セットアップ処理は可能な限り冪等にし、再実行しても設定を壊さないようにします。

## 9. Windows開発環境

### 9.1 モック環境

通常の開発、CI、障害再現は実機なしで完結させます。

モックが再現すべきもの:

- 正常な周期データ
- 起動直後の欠損
- 異常値
- 時刻ずれ
- センサ切断・復旧
- MQTT切断・復旧
- 外部送信失敗・復旧
- 重複データ
- 高頻度データ

### 9.2 シナリオ例

```yaml
scenario: weekday-home
speed: 60
sources:
  - sensorId: main-power
    metric: electric.power.active
    unit: W
    fixture: fixtures/power-weekday.csv

  - sensorId: living-temperature
    metric: environment.temperature
    unit: Cel
    fixture: fixtures/temperature-weekday.csv

faults:
  - at: 00:10:00
    type: disconnect
    target: living-temperature
    duration: 00:02:00
```

シミュレータの時刻倍率を変更できると、数日分の再送・集約処理を短時間で検証できます。

### 9.3 BルートUSB実機環境（任意）

Windowsへ接続したBルート対応USBドングルをWSL2へ公開し、必要なデバイスだけをコンテナへ渡します。この環境は、開発中にスマートメータ実機との接続を確認する必要がある場合だけ使用します。

設計要件:

- `compose.windows-hardware.yaml`等の専用差分で実機アダプタを有効にする
- デバイスパスを設定化する
- Bルート以外の機器はモックへ差し替えられるようにする
- 接続、認証、計測、切断、再接続、USB再接続を試験する
- Bルート資格情報をWindows、WSL2、コンテナのログへ出さない
- Windowsで成功しても、Raspberry Pi 4とRaspberry Pi 5の両方で同じ試験を行う

WindowsからWSL2へのUSB公開手順は、採用するWindows／WSL2／Docker構成を確定した後に`docs/setup/windows-b-route.md`等へ記載します。

## 10. 第一候補であるWi-Fi＋MQTTのESP32通信契約

### 10.1 最小payload例

```json
{
  "schemaVersion": 1,
  "messageId": "01J...",
  "deviceId": "esp32-room-a",
  "observedAt": "2026-01-01T00:00:00.000Z",
  "measurements": [
    {
      "sensorId": "temperature-1",
      "metric": "environment.temperature",
      "value": 23.4,
      "unit": "Cel"
    }
  ]
}
```

### 10.2 status例

```json
{
  "schemaVersion": 1,
  "deviceId": "esp32-room-a",
  "status": "online",
  "firmwareVersion": "0.1.0",
  "uptimeSeconds": 12345,
  "rssi": -61,
  "observedAt": "2026-01-01T00:00:00.000Z"
}
```

### 10.3 ファームウェア原則

- 設定と認証情報をソースへ埋め込まない
- watchdogを利用する
- 起動理由・リセット理由をstatusへ含める
- センサ読み取り失敗を欠損値で偽装しない
- Wi-Fi／broker再接続にバックオフを使う
- payload契約をバージョン管理する
- OTA更新を導入する場合は署名・失敗時復旧を設計する

## 11. 新しい機器の採用手順

1. 計測目的と必要精度を定義する
2. 接続方式、電源、設置条件を確認する
3. Linux／Raspberry Pi対応を確認する
4. SDK・プロトコル・ライセンス・保守状況を確認する
5. ドライバPortとの対応を設計する
6. 記録データまたはシミュレータを作る
7. 契約テストを実装する
8. 実機で接続・切断・再起動試験を行う
9. 24時間以上の連続試験を行う
10. 代替機器候補と廃止時の移行方法を記録する

## 12. 実機スモークテスト

実機リリース前に最低限確認します。

- Raspberry Pi 4とRaspberry Pi 5の両方で、OS起動後にComposeサービスが自動起動する
- 対象デバイスを安定した名前で認識する
- すべての有効ドライバが計測する
- 一つのデバイスを抜いても他の計測が続く
- 再接続後に自動復旧する
- LTEを切断してもローカル保存が続く
- LTE復旧後に未送信データが送信される
- Raspberry Pi再起動後にデータ不整合がない
- UIが表示され、ヘルス状態を確認できる
- 秘密情報がログへ出ていない
- ディスク使用量と温度が許容範囲にある
