# 再開発ロードマップ

## 1. 目的

本書は、既存OMKを停止させず、構造を一度に作り直しすぎず、段階的に再開発するための順序と完了条件を定義します。

> **決定済みの基盤前提**
> - Raspberry Pi 4とRaspberry Pi 5の両方を正式対応とする
> - 64-bit Raspberry Pi OSのみを正式対象とする
> - WindowsのBルート実機接続は、開発中のスマートメータ実機検証に限る任意経路とする
> - ESP32通信はOMK用Wi-Fi＋MQTTを第一候補とする

> **ハードウェア計画の更新（2026-08-04）**
>
> ESP32-C3、USB-C、電源およびアンテナを一体化するSEN66専用PCB Rev.A計画は**CANCELLED**であり、製造・発注の予定はない。今後は既製ESP32系デバイスを利用し、必要な場合だけSEN66接続用の最小変換基板を検討する。採用機種・電源方式・接続方式は未決定である。設計履歴は[中止決定記録](decisions/esp32-c3-integrated-pcb-cancellation.md)を参照。

ロードマップは日付ではなく依存関係を基準にします。各フェーズの完了条件を満たしてから次へ進みます。

## 2. 基本方針

- 既存の動作を棚卸しせずに全面書き換えしない
- 最初にモックと観測可能性を作る
- 共通データ契約を先に定義する
- ハードウェアごとに段階移行する
- 送信処理はローカル保存・Outboxの後に統合する
- 実機確認が必要な変更と不要な変更を分離する
- 未決定事項は推測で埋めず、判断時点と理由を記録する

### 2.1 MQTT・JSONLへのデータ収集統一

各データ取得処理は原則としてMQTTでRaspberry Piへ集約し、汎用`sensor-collector`が`omk/#`を購読してJSONLへ一次保存する。表示対象の瞬時値はlatest JSONへも更新し、dashboardは10秒ポーリングでこれを表示する。日計・履歴はParquetを後段に置く。

| 段階 | 状態 | 内容 |
|---|---|---|
| 1. ESP32＋SEN66 MQTT連携 | 完了 | `omk/sen66-001/sen66`へのpublishと再接続を確認済み |
| 2. 汎用collectorによるJSONL保存 | 完了 | `omk/#`を購読し、日次JSONLへ一次保存 |
| 3. BルートのMQTT publish | 完了 | ホスト上のBルートサービスからMQTTへpublishし、collectorがJSONL保存 |
| 4. latest JSON経路 | 完了 | Bルート、SEN66、一条power-flowを表示用latest JSONへatomic更新 |
| 5. ライブダッシュボード | 完了 | latest JSONの瞬時値とParquetの日計を表示し、10秒ごとに更新。一条鮮度切れ時はBルートへフォールバック |
| 6. Bルート専用保存の扱い判断 | 要評価 | 並行運用の安定性と欠損状況を評価して移行方針を決定 |
| 7. CSV変換機能 | 今後 | JSONLから分析・受け渡し用CSVを生成 |
| 8. 外部送信 | 今後 | JSONLまたはParquetを利用する後段処理 |

Bルート通信自体はUSBシリアル、OS権限、認証、PANA通信への依存があるため、当面ホスト上のsystemdサービスとして維持し、コンテナ化しない。段階3以降が完了するまで、BルートがMQTT対応済みであるとは扱わない。

## 3. フェーズ0: 現行資産の棚卸し

### 目的

現行OMKの「実際に動いているもの」を把握し、失ってはいけない機能と暗黙設定を明文化します。

### 作業

- 既存Node.jsプログラムを一覧化する
- スマートメータBルート通信の起動手順と入出力を記録する
- Bluetoothワットチェッカーの接続手順と入出力を記録する
- 既存Pythonアップローダの入力、送信先、再送、認証を記録する
- Raspberry Pi OSの設定を記録する
- LTE、Bluetooth、USB、シリアル、ディスプレイの設定を記録する
- systemd、cron、起動スクリプト、ログ保存先を記録する
- 使用中の秘密情報の種類だけを一覧化する
- 実機から匿名化した代表データを取得する
- 障害時の既知挙動を記録する

### 成果物

- 現行コンポーネント一覧
- 現行データフロー図
- ハードウェア接続表
- 設定・秘密情報一覧
- 回帰テスト用fixture
- 移行対象／廃止候補一覧

### 完了条件

- 各プログラムの入力と出力を説明できる
- Raspberry Pi再起動後の起動経路を説明できる
- Bルート、BLE、LTE、UIのホスト依存設定を説明できる
- 現行送信データの例を秘密値なしで再現できる

## 4. フェーズ1: リポジトリとDockerの土台

### 目的

実機なしで全体を起動できる最小構成を作ります。

### 作業

- 目標ディレクトリ構成を作る
- `compose.yaml`を作る
- `compose.mock.yaml`を作る
- `.env.example`と設定スキーマを作る
- `core`の最小起動処理を作る
- ESP32連携の第一候補としてMQTT brokerを追加する
- センサシミュレータを追加する
- health endpointと構造化ログを追加する
- CIでformat、lint、typecheck、unit test、buildを実行する

### 完了条件

- Windowsで実機なしにComposeが起動する
- シミュレータの値を`core`が受信する
- 設定不備が起動時に分かりやすく失敗する
- health endpointで主要サービス状態を確認できる
- すべてのコンテナが再現可能にビルドできる

## 5. フェーズ2: MQTT集約とJSONL一次保存

### 目的

各データ取得処理をMQTTへ集約し、センサ機種に依存しないJSONL一次保存を確立します。

### 作業

- `omk/<device_id>/<data_type>`のトピック規約を定める
- Mosquittoと`omk/#`を購読する汎用collectorを実装する
- MQTT受信時刻、topic、payload、MQTTメタデータを日次JSONLへ保存する
- statusを測定値と同じJSONLへ保存する
- 不正JSONとバイナリpayloadを破棄せず保存する
- 保存前後の統合テストを作る
- 保持期間とディスク上限の初期方針を決める

### 推奨する初期判断

- 一次保存は、Raspberry Piで扱いやすく追記・退避しやすいJSONLとする
- collectorはpayloadスキーマを解釈せず、未知のセンサを受け入れる
- DB化、集約・分析最適化、CSVはJSONL保存後の段階で行う

### 完了条件

- ESP32＋SEN66のMQTT publishをcollectorが保存できる
- 再起動後もデータが残る
- topic、payload、受信時刻をJSONLから確認できる
- ディスク容量の監視項目がある

## 6. フェーズ3: 実機ドライバの段階移行

### 目的

既存機能を一つずつ共通ドライバ契約へ移します。

### 3A. スマートメータBルート

作業:

- 現行プロトコル処理をアダプタへ隔離する
- 記録済みフレームでリプレイテストを作る
- 接続、認証、計測、切断、再接続を状態機械として実装する
- 瞬時電力・積算電力量を共通metricへ変換する
- 資格情報をsecret化する
- 必要な開発者向けに、Windows／WSL2からBルートUSBドングルを利用する任意検証経路を作る
- Windowsでは開発中のスマートメータ実機との接続、認証、計測、切断、再接続だけを短時間検証する
- Raspberry Pi 4とRaspberry Pi 5の両方で正式な連続試験を行う

完了条件:

- 既存実装と新実装の値を比較できる
- USB再接続後に自動復旧する
- 資格情報がログへ出ない
- 他ドライバなしでも単独テストできる
- Windowsの任意実機検証とRaspberry Pi 4／5の正式実機検証が同じアダプタ契約を利用する

### 3B. Bluetoothワットチェッカー

作業:

- BlueZ/D-Bus境界をアダプタへ隔離する
- 接続・切断・探索・再接続を実装する
- 記録データまたはmock GATTを作る
- 共通metricへ変換する
- 複数台利用の可否を確認する

完了条件:

- 電源断・距離外・再投入で自動復旧する
- スキャンが他処理を阻害しない
- Windowsではモックで同じ契約テストが通る

### 3C. その他のセンサ

優先順位は利用目的と現行設置数で決めます。温度、湿度、CO2、ドア開閉等を一括で移行せず、一種類ずつ契約と実機試験を完了します。

## 7. フェーズ4: UIとローカル運用

### 目的

設置者と利用者が、操作に迷わず現在状態を確認できるようにします。

### 作業

- UI技術を決定する
- 現在値画面を作る
- デバイス／センサ状態を表示する
- 履歴表示を作る
- 送信キューと通信状態を表示する
- ディスプレイ向けキオスク設定を作る
- 夜間輝度、画面消灯、再表示を設定可能にする
- UI停止と計測停止を分離する

### 完了条件

- タッチ操作なしでも主要状態が分かる
- 異常時にどの機器が問題か分かる
- UI再起動中も計測・保存が続く
- Raspberry Pi再起動後に自動表示される
- Windowsで同じUIを開発できる

## 8. フェーズ5: 外部送信とPython処理の整理

### 目的

通信断に強い送信経路を作り、既存Python処理を安全に整理します。

### 作業

- 現行送信APIとpayloadを契約化する
- Outboxを実装する
- バッチ、圧縮、再送、バックオフを実装する
- 送信の冪等性を確認する
- Pythonアップローダを独立コンテナとして接続する
- TypeScriptへ統合する価値とコストを評価する
- LTE通信量と送信間隔を計測する
- 認証情報をsecret化する

### Python処理の判断

次のどちらかを明示的に選びます。

#### 維持

- 安定しており変更頻度が低い
- TypeScriptへ移す価値が小さい
- 契約とテストが十分にある
- 独立更新の利点がある

#### 統合

- 送信制御とOutboxを一体化した方が安全
- 二つのランタイムを保守するコストが高い
- 移植後の契約テストを用意できる
- 段階移行とロールバックが可能

### 完了条件

- LTE切断中も計測・保存が続く
- 復旧後に未送信データが追送される
- 重複送信を安全に扱える
- 送信失敗理由と再送予定を確認できる
- Python処理の維持／統合方針が決まっている

## 9. フェーズ6: ESP32センサノード（基本連携は完了）

### 目的

Raspberry Piから離れた場所のセンサを、配線を増やさず追加できるようにします。

### 作業

- ESP32の標準開発基盤を決定する
- OMK用Wi-Fi＋MQTTによるSEN66連携は実装・確認済み。BLEの採用または併用が必要となる条件を整理する
- Wi-Fi＋MQTTのtopicとpayloadを新しいセンサへ展開する
- デバイス認証方式を決定する
- 共通のstatus／heartbeatと再接続方針を実装する
- 第一候補のWi-Fi＋MQTTについてLWT、broker再接続、QoSを実装する
- BLEを採用する場合はadvertising／GATT、再接続、切断検知を実装する
- センサドライバの共通構造を作る
- 汎用collectorで新しいセンサのpayloadもJSONL保存できることを確認する
- BLEを採用する場合は同じ共通計測契約へ変換するBLE adapterを実装する
- firmware versionと設定を管理する
- 電源断と、採用した無線方式の切断・復旧を試験する
- OTAを採用するか判断する

### 完了条件

- ESP32の値が汎用JSONLとして保存される
- 採用した無線方式の切断から自動復旧する
- 同一deviceIdの重複や不正認証を検出できる
- ファームウェア版をUIまたは診断APIで確認できる
- 既存Raspberry Pi直結センサと後段処理を共有できる

## 12. 技術選定の評価軸

未決定事項は、次の軸で比較します。

| 評価軸 | 質問 |
|---|---|
| Raspberry Pi適合 | ARMで安定し、メモリ・CPU・ストレージ負荷が許容できるか |
| Windows開発 | モックで完結でき、必要な開発者だけがBルートUSBでスマートメータ実機を検証できるか |
| 長期保守 | 数年後も更新・代替しやすいか |
| 障害分離 | 一部故障が全体停止にならないか |
| データ保全 | 通信断・再起動・電源断に耐えられるか |
| セキュリティ | 最小権限、認証、秘密管理が可能か |
| 観測可能性 | 状態と原因を診断できるか |
| 移行容易性 | 現行機能と並行稼働・比較・ロールバックできるか |
| AI可読性 | 契約、型、文書、テストが明示的か |
| 複雑性 | 得られる価値に対して運用要素が増えすぎないか |

## 13. リリースの段階

### 開発

- mock環境で動作
- 契約が変わる可能性あり
- 実機保証なし

### 試験運用

- Raspberry Pi 4およびRaspberry Pi 5と、限定した周辺機器で動作
- 監視下で長時間試験
- 現行実装へ戻せる

### 安定運用

- 対応ハードウェアとOSを明示
- バックアップ・復元・更新手順がある
- 実機スモークテストを通過
- 既知制約を文書化

### 非推奨

- 廃止予定日または移行条件を明示
- 代替方法を提供
- データ移行と設定移行を説明

## 14. 直近の推奨着手順

1. フェーズ0の棚卸し表を作る
2. 実機から匿名化したBルート、BLE、送信データのfixtureを作る
3. 必要な場合だけ、Windows／WSL2からBルートUSBドングルを利用する任意検証経路の最小実験を行う
4. `compose.yaml`、`compose.mock.yaml`、`compose.windows-hardware.yaml`の骨格を作る
5. TypeScriptの`Measurement`と`SensorDriver`契約を作る
6. simulatorでWindows上のend-to-endを通す
7. Bルートをfixtureで先行検証し、必要な開発者だけWindowsでスマートメータ実機を確認する
8. Raspberry Pi 4とRaspberry Pi 5の両方でBルートの正式な実機試験を行う
9. ローカル保存方式を決定する
10. Bluetooth、送信、UIを順に移行する
11. ESP32はRaspberry Pi側の契約が安定してから導入する

## 15. Raspberry Pi初期セットアップ後の運用タスク

`scripts/setup-raspberry-pi.sh`は、再現可能なDockerホストを準備する初期版です。
次の項目は設置環境や機器ごとの設計・秘密管理が必要なため、初期セットアップの
責務には含めず、各フェーズで個別に実装・検証します。

- BルートID・パスワードとセンサ固有秘密情報の安全な投入
- OMKアプリケーションおよびDocker Composeサービスの起動・自動起動
- Chromiumのキオスク表示と公式7インチディスプレイの設定
- アクセスポイント化、VNC、周辺機器のudev・権限設定
- 自動アップデート、自動再起動、ロールバック
- 計測データのバックアップ、保持期間、削除手順
- ログローテーションと、計測データからの長期的な保存先分離
